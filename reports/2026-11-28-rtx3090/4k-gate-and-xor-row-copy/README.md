# 4K prison movement, the gate and a texture used in the scene

Lucia moved from the cell to a corridor facing the barred gate. The 120-second interval presented 1,598 frames, averaging **13.32 FPS**. Its slowest and fastest five seconds averaged 7.4 and 16.8 FPS. The longest frame took 518 ms. In a separate 120-second interval starting beside the bars and ending facing a closed gate, the game presented 2,275 frames, averaging **18.96 FPS**. Its slowest and fastest five seconds averaged 14.6 and 23.4 FPS. The 95th-percentile frame took 69.8 ms and the longest 154 ms. Both intervals used native Series X settings and 4K output. No five-second window reached 25 FPS. The gate window includes time looking at the gate, and the captures do not establish how much distance Lucia covered during it. [Cell boundaries](cell-route.jpg) · [Gate boundaries](route.jpg) · [Cell frame times](cell-metrics.json) · [Gate frame times](metrics.json)

After the timed gate sample, the camera turned into the common room. Between the first and last camera captures only 12 presents occurred in 13.388 seconds, including a 10.094-second gap. The captures themselves were made during this separate camera test. The busiest Windows thread accumulated 9.281 CPU seconds over 9.327 seconds of OS samples fully inside the gap. Its role is unknown. The matching renderer report covers 11 frames, so its stage times cannot be attributed to the longest frame individually. The close-up captures only part of Lucia's face in shadow. The interview lighting and the original moving skin artifact remain to be verified. [Camera sequence](quality-angles.jpg) · [Face detail](face.jpg) · [Camera timing](post-camera.json)

The runtime confirmed a **256 × 256, four-byte-per-texel SW_64KB_R_X** texture was successfully tiled back into game memory in the prologue. The reflection limiter recorded at least 10,000 executions. Free physical memory during the gate window stayed above 5.05 GiB. The Windows host retained control and the measured game closed on request from the driver. ## Reducing the CPU cost of the observed layout

After the game closed, I changed the copy loop to compute the tile-row base and the row XOR contribution once per row, then advance the tile base per block across the row. The 16-byte inner copies use a fixed length, with a separate partial copy at the edge. The GPU address equations, output bytes, row padding and display resolution are preserved. On the Ryzen 7 3700X, the exact 256 × 256 × 4 layout observed in the game took **181.65 → 22.30 µs** to tile and **212.15 → 25.30 µs** to detile (medians). Each variant passed all 24 format tests, including the AMD reference address hashes for both console models. The gameplay numbers above were recorded before this CPU change. [Source patch](xor-row-copy.patch) · [Samples](samples.csv) · [Original tests](tests-before.txt) · [Modified tests](tests-after.txt)

The two release-optimized copies were compiled with the same Rust toolchain and native CPU target. Four separate processes ran in before/after/after/before order. Each size provided 48 measured samples per variant after warm-up. Both directions are measured independently with pitched synthetic bytes and checked row contents. The patch applies to the [tested GPU readback and XOR baseline](../rtx3090-xor-texture-readback). To reproduce, invoke run.py with paths to rustc, that source checkout and a writable work directory.
