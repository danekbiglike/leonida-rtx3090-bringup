# RTX 3090 readback of successive buffer uploads

Two separate runs on the RTX 3090 reproduced two ordering errors in our row-copy renderer. Both checks passed after applying makmatvey's VIctory-NVIDIA change. All inputs were generated by the tests. [Upstream change and tests](https://github.com/trustno1-coder/VIctory-NVIDIA/pull/874) · [152 individual reads](gpu-readback.csv)

| GPU read | Row-copy renderer | With the ordering change |
|---|---|---|
| Two successive copies of 8 MiB + 256 bytes in one command list | Both reads started with `0x51`. The first should have started with `0x21`. | The first read contained `0x21` throughout and the second contained `0x51` throughout. |
| Three submissions sharing the same PC-memory destination, six rounds per run | In each run 12 of 18 reads failed. The first two submissions received the last submission's bytes. | All 18 reads per run matched the expected 256-byte patterns. |
| Three submissions using the card-memory control, six rounds per run | All 18 reads per run matched. | All 18 reads per run matched. |

The command-list test checks every byte in both results. The original renderer deferred the large copies. To reach its readback check, the test's expected placement count was set to zero for that renderer. Both processes had `VICTORY_COPIES_IN_PLACE=1`. The patched renderer placed the two copies and used the corresponding expectation. The three-submission test held the queue with a fence while the CPU prepared distinct values for all three reads. The same test module was used in both builds, SHA-256 `8fda28fbb113e9f98540d059f4aef242aa1465e70f4bad8c92d610ab6f67bf83`. The local port required an empty upload field in an existing synthetic flight fixture. [Fixture adjustment](test-fixture.patch)

These measurements establish that two real GPU reads could receive newer data than their draw or dispatch requested. The measurements contain no game scene. The effect on Lucia's lighting and the prison frame rate requires a gameplay comparison.
