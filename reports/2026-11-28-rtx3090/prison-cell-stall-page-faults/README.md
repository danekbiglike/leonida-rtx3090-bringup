# What the RTX 3090 renderer did during its 18.67-second prison-cell frame

The renderer's page-fault counter stayed flat for **17.009 consecutive seconds inside the 18.673-second frame**. Over those 17 seconds its Windows process read counter advanced by 290,135 bytes. In the preceding 17.014 seconds it recorded 2,777,273 page faults. In the following 17.010 seconds it recorded 975,116. These are all process faults, including soft faults. Windows sampled the process once per second. The CSV includes only intervals with both endpoints inside the same phase. [Per-second samples](faults-and-reads.csv)

The frame contained 5,823 draws. The renderer attributed 18.198 seconds to buffer preparation. That timer includes time spent waiting within the measured functions. The samples rule out a sustained stream of new process page faults during the middle of this stall. They leave open a single blocking operation, a lock wait or a scheduling delay. The process I/O counter also omits some system-managed paging activity. A window capture was saved during the stall, so this recording includes measurement activity. Event tracing or finer-grained renderer timings would be needed to identify the wait. [Original frame timings and captures](https://github.com/danekbiglike/leonida-rtx3090-bringup/tree/e85aad5105c88c96ebd87e7e824af451a0b6ecd0/reports/2026-11-28-rtx3090/paired-lighting-prison-cell)

We also exercised a resident-memory limit change on the same renderer in a separate 4K prologue run, with texture reads set to proceed while the memory map was busy. Windows accepted 16 → 17.5 → 16 GiB for 60 seconds each and retained at least 4.28 GiB of available physical memory in the middle window. The camera moved on its own during the sequence. The windows had medians of 554, 3,973 and 1,062 draws per present. That difference prevents attributing the FPS change to the limit. The normal launcher keeps its prior limit.
