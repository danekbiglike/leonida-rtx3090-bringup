# RTX 3090 buffer transfers during an interrupted 4K run

The renderer on the experimental submission branch closed before the first timed prison walk. The last accepted frame had 6,618 draws and arrived **24.659 seconds** after its predecessor. The game later attempted a null write and exited with `0xc0000005`. This run supplies no corridor FPS score. The memory sampler recorded at least 3.94 GiB of available physical memory throughout the run. The exception and the pauses have not been shown to share a cause.

Nineteen long buffer refreshes overlapped this frame. The timings cover concurrent work and cannot be added. One worker requested a 2 MiB span and refreshed 1,703,936 bytes. Its timer recorded **7,489,935 µs in the transfer** out of **7,489,938 µs total**. Acquiring the copied-page lock, scanning and preparing the ranges took about 2 µs combined. Windows observed that worker waiting at all ten scheduler snapshots taken inside its transfer. Its reported wait reason was `Executive`, which does not identify what it was waiting on. This narrows the investigation to a routine that both transfers bytes and waits for workers. [Measured transfers](transfer.csv) · [Frame and scheduler samples](long-frame.json)

The submit branch passed the targeted renderer tests, selected the validated 16 × 2 lighting group on the RTX 3090, and logged reuse of its submission write journal before the failure. The most recent completed 4K gate-to-interview run on the row-copy branch averaged **16.81 FPS**. A follow-up on that branch tests processing copies of 1–8 MiB on the worker that already owns their page lock, preserving the original stripe boundaries.
