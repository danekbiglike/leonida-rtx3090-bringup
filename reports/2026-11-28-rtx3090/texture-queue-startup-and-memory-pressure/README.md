# Texture queue build on RTX 3090 and memory pressure during startup

The new renderer reached the first 3D scene on the same RTX 3090. The scene still showed visible bands. The existing low-memory guard stopped the test 345.203 seconds after launch with 1.45 GiB of physical RAM available. The game did not reach the timed corridor. Peak renderer private commitment was 30.40 GiB and the peak working set was 16.00 GiB. The game and benchmark processes exited. [One-second system memory samples](memory.csv)

The executable was built with its own Cargo target directory. Forty descriptor tests, two range tests, five pool tests and the wave shared-memory regression passed. One existing test was ignored. On the RTX 3090 all eight previously failing compute shaders passed DXIL validation and D3D12 pipeline creation. Using the real embedded container and the test game's cache directory, offline warming found eight requested shaders and translated eight in 4.3 seconds. An immediate second run found all eight in the cache and took 0.3 seconds. [Queue patch and controlled timings](../bounded-texture-queue-order/) · [Embedded container scanner](../embedded-shader-cache-keys/)

The updated benchmark launcher starts shutdown when available physical memory falls below 3.25 GiB after three consecutive decreases totalling at least 512 MiB. Existing physical and commit limits still apply. We tuned the additional rule against six recorded runs. Replaying the final run with the compiled guard triggered it at 337.187 seconds with 3.14 GiB available, 8.016 seconds before the actual shutdown trigger. It triggered earlier on both recordings that reached emergency memory pressure. It stayed inactive on the four other recordings. These timings describe replay decisions. RAM available after shutdown can vary as Windows releases the renderer's resources.
