# GPU resource retirement queues on a Ryzen 7 3700X

With eight producer threads pushing 2,500 records each, the median elapsed time to enqueue 20,000 records fell from **1,784 µs to 365 µs** when the workers used separate queues. Draining the finished entries took **220 µs** for one queue and **398 µs** for 32 queues. Median push-plus-drain time in the same round was **2,018 µs versus 751 µs**. With four workers the corresponding totals were 1,001 µs versus 400 µs. One worker was slower with the sharded configuration, 90 µs versus 75 µs. The change comes from [KyleS98's VIctory-Neo](https://github.com/KyleS98/VIctory-Neo/commit/9165dd03eb85432d691594d76df8a157fa960149). Each retiring thread takes one of 32 queues and the completing thread checks all queues for finished submissions. We added a release-order test for four local queues. Its fences include an out-of-order entry and a future submission. It checks the number of objects actually dropped at each fence and verifies that every queue lock is available to each destructor.

The benchmark uses the submission-fence queue and drain algorithm with synthetic records. Threads start together, each touches its own queue in the sharded run, and there is a check that every record arrives before draining. It alternates the two settings, drops two warm-up pairs, and reports nine pairs per worker count. The timer includes synchronization with the workers and excludes creating and joining them. It measures CPU queue contention, not GPU destruction cost or in-game frame rate. [Tested code and fixture](tested-queues.patch)
